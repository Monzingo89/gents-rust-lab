# Native owned-component input recipes

The native MCP layer now supports an explicit owner-frozen recipe for dependent positional arguments. This extends the typed boundary in [document 100](100-typed-component-edge-boundary.md). It does not yet expose recipe planning in the CEO workflow or establish actual local-company component-chaining competence. Existing independent-root input hashes keep their original meaning, and the public office remains on its last task-qualified build while this native extension is checked.

## Frozen contract and resolution

Each `required_owned_rust_calls` entry requires exactly one of `input_sha256` or `input_recipe`. A literal input hash still binds the complete canonical positional tuple. A recipe instead holds a complete tuple template and 1–8 explicit references, each identifying an empty argument slot, an earlier approved producer artifact-binding path and a return-value pointer. Recipe identities are tagged `owned_positional_receipts_v1`, distinct from literal hashes. The enclosing approved intake digest binds the recipe, actor, source/API/function pins and all other literal arguments.

An indexed artifact reference has `field=arguments`, `argument_index`, `path` and an explicit `pointer` (empty pointer means the complete return value). Indexed references are restricted to the owned Rust adapter and require their matching frozen recipe. Every producer must be an earlier owned whole-`/output` binding with its own frozen specification. Duplicate slots, nonempty replacements, missing/forward/cyclic producers and mismatched recipe/binding references fail admission. Limits remain sixteen artifact bindings and eight references/arguments per recipe; argument data is bounded to 8192 bytes. Ordinary top-level table-input references retain their previous format and behavior.

`owned_recipes` separates recipe validation, receipt-backed resolution and successful-observation checks from `owned_components` invocation. `bound_sources` remains the common canonical source observer. It resolves a reference from the current run and policy epoch, with exact actor/tool/argument/result/projection identities, stored value integrity and successful canonical worker audit. An owned projection additionally needs a matching `passed=1` owned-invocation observation. A failed invocation's null output is never accepted as a successful unit value, even when its outer MCP call has a completed receipt.

The resolver reads source snapshots through the existing confined descriptor adapter, verifies current source/API pins, checks producer/consumer wire compatibility and requires the selected value to exist. It then validates the entire resolved consumer tuple. Caller-provided arguments must equal this exact tuple; a model value, output file, altered literal, coerced integer or default branch cannot replace it. Parent-source admission is read-only, and recursively rechecks ancestor pins and recipes. A per-resolution admission cache avoids repeatedly validating shared ancestors; its lifetime is one trusted native operation and its key includes actor and exact argument identity. No candidate is compiled or invoked during resolution/admission.

The normal native execution adapter repeats these checks before isolated invocation. The successful result records the actual input hash plus recipe identity and lineage: run, epoch, producer binding/actor/function/source/API identity, approved argument hash, native result hash and selected value hash. No raw selected values are copied into lineage metadata. Current lineage is also required by owned-source observation and completion, so a mismatched lineage record cannot qualify merely because an output value looks plausible. Existing per-agent `memory_from` gates and current producer tool grants remain required; the current common observer conservatively requires access to any ancestor it traverses.

## Compatibility and lifecycle

Two nullable observation columns retain recipe and lineage digests. Migration adds columns without rewriting old rows. Read-only preparation can verify a legacy observation before migration without changing the schema. Literal results retain their previous result fields and hashes; recipe fields are only attached to dependent results. Legacy completion uses null recipe/lineage identity, so a derived observation cannot masquerade as a historical literal invocation.

Actual execution still requires an approved/running job. Internal source admission for evidence checking performs no invocation and can verify a completed job. Thus completed dependent receipts remain independently checkable without reopening terminal execution. Completion repeats current source/API/input/recipe/lineage checks. It is an evidence gate, not a model verdict, global source promotion, memory-learning claim or industry assurance.

The tool remains `owned_rust_call`, with the existing process-scoped stdio/SSE adapters and thirteen-tool registry. Its input fields remain `binding_id` and positional `arguments`; callers cannot supply source text, paths, function names, recipes or permissions in a tool request. Recipes reside only in owner-approved intake. The descriptor now describes both modes. Output projection policy remains bounded by the installed schema; receipt-lineage metadata is not a new general graph projection.
