# Native Python diagnostics and a rejected repair loop

The local company can now request `python_check` through native MCP. The tool
uses the [read-only snapshot boundary](138-python-snapshot-verification-experiment.md)
and an owner-frozen contract: actor, explicit source files, immutable unittest
suite/hash and installed interpreter hash. The harness binds the current
source/run/policy/implementation identity before ordinary action review. Native
execution rechecks it, and the ordinary native privacy/audit boundary applies.
Both stdio and private HTTP/SSE integration checks pass.

This is host-authored infrastructure. `reported_pass` is diagnostic evidence,
not independent correctness, source promotion or automatic company acceptance.
Generic shell replay rules and existing frozen jobs are unchanged. The original
observer job remains unqualified; a fresh job needs an explicit diagnostic
contract and grants. Setup and exact boundaries are in the [MCP guide](../mcp/README.md).

## Actual local-company trial

One isolated, owner-approved trial used the installed Qwen3-Coder-30B for
separate worker/admin calls, with only file read/write, `python_check` and finish
grants. It had no email, web, shell, download, training or delegation capability.
The host seeded a deliberately wrong Python function and froze four tests before
generation. The requested repair preserved unique strings in first-occurrence
order, including case and Unicode, without mutating the input.

The worker first obtained `reported_fail`, authored a correct repair and read it
back. Two later checks of that source returned `reported_pass` with native
receipts. A host source review plus six contract examples and 300 deterministic
generated-list probes also passed for that source. Those extra probes were
written after generation and are not a preregistered held-out benchmark.

The worker then changed the passing implementation to case-insensitive
comparison. The unchanged frozen suite caught that regression. It repeated
ineffective repair proposals. One source-linked internal all-hands clarification
provided no implementation code and changed no criteria or permissions; it did
not recover the task. The owner stopped the trial after **358.09 seconds and 30
recorded model replies**, with confirmed `cancelled` status and no pending effect.
The owned test runtime was then shut down. Original journals and rejected source
remain retained; no existing office task was cancelled or modified.

Recorded usage: **213,963 input tokens, 5,533 output tokens and 20,510 cached
input tokens**, as separately reported by the runtime. Cached input is not added
to the input total. Reasoning-token accounting and usage for the interrupted
call are unknown. Provider fees were **$0**; hardware, electricity, installed
models and frontier host development are separate. No weights changed or models
were downloaded. This is a negative autonomous-repair result, despite successful
tool execution. The earlier passing source differs from the final source and
does not qualify the final candidate.

## Evidence-driven follow-up

Workers now receive a bounded `python_diagnostics` view before planning. It reads
the current explicit source and current owner policy, then looks up a native
diagnostic observation with the same run, actor, contract and implementation
identity. It verifies the exact canonical receipt and result hash. Changed source,
changed policy, missing/forged receipts and a later uncertain attempt cannot
inherit an older passing observation. Tests exercise these cases. The view
executes no tests, grants no authority, erases no history and caches no acceptance.

The purpose is to make completed prerequisites and newly invalidated evidence
explicit without copying full journals into every prompt. **A reduction in local
tokens or repair regressions has not yet been demonstrated.** A fresh bounded
company trial is needed; the cancelled run must not be retroactively described
as having used this follow-up. Independent acceptance and the broader durable
continual-improvement controller remain unfinished.

[Reviewed public evidence](evidence/local-python-diagnostics-2026-11-15.json)
records source hashes, native check scope, the failed trial and its limits. The
local website reference now lists the sixteen native tools. This working-tree
change is not proof of GitHub publication or production deployment.

Final verification: strict workspace Clippy, 546 offline workspace tests, a fresh
build, six snapshot checks, 31 broker checks, five research-default checks,
synthetic factory/autonomy recovery smokes and local site checks passed.
Twenty-seven opt-in/platform tests remain ignored by the ordinary workspace run;
they are not counted as passing checks. The follow-up has native regression
coverage but no new live-model efficiency result.

The [subsequent bounded trials](140-bounded-python-review-submission.md) retained
another context-only failure, then completed one explicitly approved candidate
submission using native custody and a host-compiled review request. This earlier
negative result and its source snapshot remain historical evidence.
