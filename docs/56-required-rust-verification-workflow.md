# Required Rust verification workflow

`rust_workflow.rs` compiles the two steps already required by an owner-frozen Rust assignment: fully read the newly written source, then call `rust_verify` against its frozen acceptance file. The CEO still selects the actor and write/read/verification tools during planning; the local author supplies the function implementation. This compiler supplies only deterministic control flow after an actual native write, never a candidate implementation or an acceptance answer.

The compiler checks the actor, worker phase, current policy epoch, frozen source path, approved staffing tools, current read/verification grants, zero-cost completed native receipt, exact argument/result hashes, written byte count and source hash. Failed or uncertain effects, mismatched receipts, absent grants, another actor/path and oversized source produce no plan. Empty source can still receive a real native admission failure; generating followups does not imply valid Rust. No mutating followup or write replay is generated.

Mandatory readback and verification precede remaining model-proposed calls. Exact duplicate read/verification calls are removed; other queued calls retain their relative order. The completed write and its required followups share one checkpoint save. A failed tool clears remaining work; failed native acceptance clears queued followups before checkpointing and returns the real failure to local recovery. Each call still passes the existing argument checks, independent authorization, live governance, replay accounting and native receipt capture. Final QA and source-bound acceptance/readback gates are unchanged. Source remains an unpromoted run artifact.

`rust_verification_plan_compiled` events visibly distinguish this host-compiled workflow from model proposals. Reports and curriculum admission record `host_compiled_rust_workflow_plans` and `host_compiled_rust_planned_followups`. These count plans, not executed calls or saved inference: a denied/failed call can stop a plan, and a model might already have proposed equivalent steps. Actual execution remains in the tool journals and canonical receipts. No counterfactual token saving or task success is inferred from a plan.
