# Native runtime bundles

The harness previously started every native MCP child from `target/debug/gents-local-mcp`. A build could therefore change a later tool call's executable while a long company run still used an earlier harness. Pre-launch file fingerprints recorded an observation but did not select a stable child executable. This is an upgrade-consistency gap, not evidence that a historical run actually executed mixed binaries.

`scripts/mcp-runtime-bundle.mjs` now owns native snapshot preparation separately from tool execution, permission checks and task verification. It copies the owned harness, MCP server, SQLite bridge and acceptance parser from a completed build into `data/mcp-runtime-bundles/<content-id>/`. It checks ordinary owner-controlled sources, bounds each executable to 512 MiB, hashes streamed bytes, detects source changes during copying, flushes the copied files, writes a bounded manifest and publishes a read-only directory. Copies are ordinary separate files, never source hard links. Identical executable sets reuse the same content-addressed directory only after its manifest and all four files are revalidated. Corrupt caches fail; they are not silently overwritten or used as a reason to select another build.

The launching host supplies the relative manifest identity and exact manifest digest in `GENTS_RUNTIME_MANIFEST` and `GENTS_RUNTIME_MANIFEST_SHA256`. These fields are absent from model/tool input schemas. `mcp/src/runtime_bundle.rs` validates the fixed namespace, manifest schema/role names, owner/permissions, sizes and exact MCP bytes before each child launch. Partial configuration, missing files, changed hashes, writable sealed paths, symlinks and hard-linked files fail without build-directory fallback. With neither field supplied, explicit development-directory behavior remains available for existing direct invocations. Newly issued curriculum trials require verified bundle mode.

`gents-harness --native-runtime-probe` validates the actual selected binding before reading configuration, recovering jobs or starting models. The normal harness also validates requested binding before those activities. The launcher probes the copied harness with a minimal environment and an impossible CONFIG path so the known older harnesses, which ignored CLI arguments, fail before normal startup. Both benchmark runners additionally check `/api/mcp/catalog` for the expected verified manifest identity and selected MCP path before planning. A server that silently ignores bundle selection cannot issue model work through these launchers. The normal company launcher uses the same snapshot/probe path. Existing scoped policies, revisions, approvals and current-state evidence remain live and independently enforced; a bundle grants no authority.

Reports preserve `runtime_bundle`, its startup probe/binding and any prior bundle. Earlier `runtime_build` fingerprints remain observations of build-directory files; they are not retroactively reinterpreted as bundle execution. Bundled SQLite helpers are selected for subprocesses launched by that harness. Independent host journal/verifier processes remain separately managed. stdio/SSE selection is unchanged.

The implementation does not pin the compiler, llama-server, model files, Python helper source, shared libraries, the OS or arbitrary external components. It is not a reproducible build, authenticated process attestation, an atomic hash-and-exec transaction or a defense against a privileged same-user process that can change permissions/rewrite files. It confines model-controlled workspace operations from runtime selection and prevents ordinary builds from replacing selected native copies. Windows owner/ACL validation is not implemented and bundle launch fails closed there; Linux/macOS ownership checks do not establish universal portability. No old snapshots are automatically deleted while their run references may still matter.

Focused tests exercise source rebuild survival, deduplicated reuse, cache corruption, missing/symlinked inputs, exact manifest binding, partial/mismatched selection, writable/tampered copies and launcher-environment preservation. A separate integration test runs real native arithmetic through both stdio and SSE from the copied MCP executable after replacing the build path, then requires a tampered copy to fail before another receipt. The legacy-build probe was also executed against an actual pre-feature snapshot and rejected it before server/model startup. These are runtime consistency checks, not domain competence or industry compliance evidence.
