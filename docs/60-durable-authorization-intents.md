# Retain unexecuted intents across authorization failures

During the sixth-task reasoning trial, the local author wrote a new candidate, but the controller discarded its queued read/check steps when reviewer context preparation failed. Events 3351–3363 document consumed steps without native execution. Events 3374–3387 document an additional author plan followed by the same preparation failure. A retry must not silently lose unexecuted work or treat an old verdict as current authority.

`intent_queue.rs` separates intent selection from execution. The checkpoint now retains one `review_intent` alongside remaining `plan_queue` entries. It contains quarantined proposal data only, with no authorization or effect claim. Selecting an existing queue head transfers it to the retained slot in the same atomic checkpoint save. Fresh single actions and the first action of new plans also enter that slot before authorization. Historical checkpoints without the field still load.

Review preparation failure preserves the selected proposal. A `queued_intent_retained` event records its hash, absence of execution and requirement for fresh authorization. Restart selects that exact intent before later steps or another author call. Actor identity, current grants, schema, source preconditions, evidence dependencies, replay limits and independent review are all checked again. An explicit denial, invalid request or replanning disposition discards the retained proposal; it never bypasses a veto. No permissions or artifact bytes are supplied by this module.

For external tool actions, the selected intent is consumed only when its exact proposal transfers to the separate write-ahead `pending` record, in one checkpoint save before effects. The existing uncertain-effect recovery guard still applies after an interruption; the retained slot is not an effect-replay mechanism. `ask_user` and `finish` remain control actions and consume the selected intent after authorization; final QA for `finish` remains separate. Final-QA preparation failures are not made durable by this change.

The Rust checkpoint test covers restart, unchanged ordering, a mismatched consume rejection and the pending-effect boundary. The separate `intent_retention_smoke.py` test uses a disposable company and simulated reviewer failure through the real HTTP server. It observes no file effect before a verdict, restarts with a working reviewer, obtains fresh authorization, writes once, then reads in order without a new author call before the first effect. These are infrastructure tests, not local model competence or estimated token savings. No live benchmark checkpoint is seeded or edited by the tests. The smoke is included in `scripts/check.sh`.

All 333 default Rust tests, strict Clippy and the focused HTTP smoke passed, with 19 opt-in probes excluded. The real benchmark completed on its already-running earlier host and therefore is not evidence that this queue repair saved it tokens. Its next fresh run can exercise the new checkpoint behavior.

The full `scripts/check.sh` subsequently passed, including existing uncertain-effect, cancellation, veto and restart smokes, the new intent-retention smoke and production UI build.
