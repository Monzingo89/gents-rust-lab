# CEO-selected owned calls over immutable owner data

Previous qualified workflows supplied exact prepared invocation IDs and functions before the CEO designed the graph. This phase adds a discovery-only draft: the CEO can select functions from an owner-selected catalog and map positional arguments to named owner data or earlier proposed results. The draft cannot execute, staff a team, install policy, promote a source or establish task completion.

## Data, selection and adoption

`owned_argument_data` is an immutable JSON object with at most sixteen bounded names and 8,192 serialized bytes. It is captured with selected owned interfaces, excluded from source bodies and explicitly included in the local planning packet. Changing captured values requires a new conversation. Existing conversations without this field keep their prior shapes and planning modes.

The current `owned_selection_v2` planning view separates an empty clarification (`status=question`) from a concrete preparatory draft (`status=selection_review`). Both require empty native sources/artifacts, empty staffing and empty completion criteria. Native runtime validation enforces this independently of the constrained decoder, including when a response omits the proposal field. An initial clarification has an empty `owned_selection_proposal`; once requirements are clear the CEO uses `selection_review` to propose up to eight calls with its own IDs, selected component/function identities and positional references:

* `{kind:data,data:OWNER_KEY,pointer:JSON_POINTER}` copies an exact value from captured data.
* `{kind:result,source:EARLIER_CALL,pointer:RETURN_POINTER}` proposes an unresolved positional slot.

The pure `owned_selection` module rejects unselected functions/components, wrong arity, invented literals, missing data, malformed pointers, duplicate IDs, noncausal dependencies and unknown fields such as source bodies or actor grants. The owner-facing result includes the original model proposal, resolved literal arguments, unresolved null slots, proposed edges and a digest bound to session/revision, catalog and data. This is a draft, not an ABI-valid or executable graph: private source custody, literal ABI validation, edge typing and runtime branch presence remain later obligations.

The UI displays the exact pending draft. “Use these calls for preparation” copies only invocation data into the existing preparation form; it sends no request, approves no job and installs no policy. The owner's next submitted message uses the existing authenticated preparation API. That API rechecks source ownership, source/API pins and literal ABI shape, then retains the source snapshots and typed templates. The CEO subsequently selects actors, final dependency edges, outputs and stage criteria through the already tested prepared-graph flow. Its ready graph still requires normal frozen intake, owner approval, governance and native acceptance.

An exact owner copy records the model proposal's preparation provenance; edited ordinary owner inputs do not acquire that provenance. Frozen intake checks copied owner data and selection provenance against retained planning state. Earlier proposed edges are context for later planning, not an already approved final graph. No model-selected function executes merely because the owner prepared it.

## UI and compatibility

The extra controls are advertised only when `/api/config` reports `owned_selection_drafts` for company tools mode. Older office binaries do not expose the new controls. Switching company, connection, token or conversation clears selection data and review state; logout also clears the conversation object. The review uses text rendering and copies only allowlisted invocation fields. Existing manual invocation entry remains available.
