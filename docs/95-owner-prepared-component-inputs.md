# Owner-prepared component inputs

The host can retain a selected component's exact source bytes and invocation data during CEO clarification, derive invocation requirements from the accepted CEO actor selection, and stage those retained bytes only at approved job admission. The browser no longer needs to upload library source or invent actor-bound requirements manually. This extends [owner-scoped discovery](94-owner-scoped-component-discovery.md); actual invocation remains the existing governed native `owned_rust_call`.

The separation follows the MCP maintainers' distinction between descriptive hints and runtime enforcement: annotations alone cannot provide enforcement, so the host must enforce the boundary. See [Tool Annotations as Risk Vocabulary](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/). This implementation treats interface metadata as information; it does not derive permission from descriptions, model prose or historical fixture PASS labels. It is not an MCP protocol-version migration or a compliance certification.

## Data and authority flow

1. The owner selects up to four owner-visible component interfaces before starting a conversation. During clarification they may add up to eight invocation inputs, each containing only `id`, `component_id`, `function` and positional `arguments`. Caller-supplied actors, source code and paths are unsupported. IDs are immutable; later clarification may add new IDs.
2. `owned_inputs::prepare` checks the current owner-filtered catalog against the captured source/API/origin identities. A private host-only catalog operation returns sealed source bytes. The Rust ABI adapter parses that exact source and validates argument types/ranges without compiling or invoking it. Unsupported encodings fail before a planning turn is retained.
3. Inside the planning transaction, a separate `ceo_owned_inputs` table retains private source bytes and exact manifests. Conversation state contains metadata and exact tool input declarations, never library bodies. The CEO receives the selected schemas, source/API identities and the mapping between each prepared input and function. It chooses the real source actor and output writers through the existing native graph.
4. A ready plan must give every prepared invocation a native output artifact and retain its exact arguments. During intake, the host derives `required_owned_rust_calls` from the accepted plan's source actors and retained source/API/function/input identities. Owner-edited artifact bindings must preserve those input identities and source actors. Supplied conflicting requirements are rejected. The frozen job includes the retained invocation manifests in its approval digest.
5. Browser review compares the returned manifests with the saved conversation before showing approval. Expected manifests stay outside the outgoing intake object to avoid duplicating large owner inputs. The review displays exact source hashes and actor/function/input identities. Editing invocation data hides the execution controls until a new planning turn is submitted.
6. `company::admit` still requires approval and the exact frozen task. Only then does `owned_inputs::stage` check the frozen manifests and current source-company ownership, stage the exact retained source, and perform complete readback through the shared descriptor-relative `owner_staging` adapter. Existing different bytes and aliases are rejected, never overwritten. Matching bytes are idempotent; partial staging remains inspectable without model/tool replay.
7. Native execution independently checks active owner/company/run/actor policy, the source/API/function/input pins and supported ABI, runs within the existing supported sandbox, and records native evidence. Approval, current grants, independent completion review and protection of library input paths remain in force. Source staging itself grants no tool access and executes no candidate.

`owned_inputs.rs` owns preparation/custody and binding lifecycle. `owned_catalog.rs` remains the disclosure/private-host inspection adapter. `component_api::validate_arguments` provides the same bounded codec validation used by actual invocation, without exposing generated driver code to models. `owner_staging.rs` shares the exact filesystem mechanics with the existing JSON-table attachment adapter; JSON uploads retain their original table-only validation. No generic Rust-upload endpoint, arbitrary path input, shell tool or new actor capability is added.

Storage is bounded to eight invocation records, four source paths, 8192 source bytes per component and 16 KiB retained manifest metadata. Metadata requests and exact native input declarations retain separate bounds. Stored queries have row/byte limits and validate complete source/API/input identities on every load. Source bodies and raw candidate errors are absent from HTTP planning responses and staging audit events. The private host snapshot operation is not a browser or actor endpoint.

## Evidence and limits

Rust custody tests cover atomic rollback, private source exclusion, immutable inputs, unsupported actor/source fields and argument types, the actual compiled artifact-binding schema, CEO actor binding, rejection of changed inputs/actors/API metadata, missing artifacts, approval-before-staging, idempotent exact readback, workspace conflicts, ownership revocation and corrupt private bytes. The source used in these tests deliberately cannot terminate; no candidate invocation occurs during preparation or staging.

`owned_discovery_smoke.py` exercises real private HTTP ownership filtering and source preparation. An unavailable local planning policy proves retention without inference. The test explicitly seeds a simulated ready CEO verdict, then checks real frozen intake/approval, host-derived actor bindings, source manifest preservation and rejection of forged requirements. No candidate function or model is invoked by this protocol smoke. It is not a task-competence result.

Node checks cover exact review preservation, bounded function-input templates, source snapshot integrity and aliases. The earlier real local-company reuse qualification remains historical evidence for the previous bundle and exact fixture. It does not by itself qualify this new ingress path. A fresh actual local-company reuse trial through this preparation path, then harder composition benchmarks, remains necessary before claiming that broader workflow as qualified. General capability, acquisition/training automation, other hardware/OS isolation and industry assurance remain incomplete; the broad goal stays active.

Verification logs use `data/mcp-basement-verification/owned-preparation-*`. No paid model/service, download, training, frontier task implementation or benchmark answer is supplied by this architecture work. Local compute and Codex development credits are separate costs.
