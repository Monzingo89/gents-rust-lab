# Outcome-only local planning

The third reviewed curriculum level tests whether the local CEO can choose a native workflow from file inputs and requested results. The fake user supplies two SHA-256-pinned JSON files and describes the required outputs, matching policy, multiplicity, exact boolean filter and grouping behavior. Its planning attachments contain no transformation templates or dependency graph. The independent evaluator retains an expected graph and exact results outside model prompts.

This is a bounded composition test, not evidence of arbitrary task competence or model training. The first two qualified levels used owner-supplied transformation templates. Their qualifications remain distinct from this harder level.

## Composition boundary

Native tools declare `data_input_fields` in the implementation catalog. Only deterministic, read-only tools with a nonempty declaration are eligible for CEO-designed derived sources. Currently those are `table_join` and `table_aggregate`. Every declared data argument must be an empty array bound to an actual earlier native result through `argument_sources`. The CEO chooses metadata such as keys, columns and grouping policy from the user's requirements. It cannot invent rows, introduce another file reader, override fixed attachments, or gain write/network/memory authority through this mechanism.

The constrained planning schema exposes these alternatives only when every attachment is fixed, without an owner-supplied derived template. Template-based planning retains its original boundary. Derived names use `transform_NAME`; fixed input IDs remain reserved. The compiler rejects missing producers, cycles, invalid projections, ambiguous owners, repeated staffing actors, and missing permissions.

Referenced immutable input roots may be materialized by the compiler. This closure only copies existing owner attachments into source declarations. It never chooses a transformation, changes its arguments or grants a tool. The raw model draft remains in the conversation; `host_compiled_roots` records additions separately. Outcome-only review compares every effective transformation against the actual raw local CEO draft, so a host-authored solution cannot pass as model planning.

The proposal is still subject to reviewed freezing, owner approval, exact installed policy, native receipt enforcement, stage handoffs, output write/readback and independent QA. Schema restrictions and model instructions complement those controls; neither replaces them.

## Evidence and diagnostics

Every completed local planning reply, including rejected drafts, retains measured usage and local execution provenance in the canonical planning audit. Rejected output is represented by its hash and a bounded structural diagnostic: IDs, tools, owners, references, output paths, pointers and encodings. Rejected arguments, rows, task prose and guessed numeric answers are excluded from that diagnostic. Privacy validation runs before retention. These shapes are explicitly unverified and cannot become execution facts.

Review feedback for this level names the failed policy or output requirement without dumping the evaluator's expected graph or values. Join column declarations and dependency declarations may be reordered because they are metadata; row order and exact native receipt hashes remain significant. The shared reviewer is used by execution and independent verification.

The curriculum journal checks the complete prerequisite chain against current fixture versions. A stale first-level qualification cannot indirectly authorize a third-level challenge through an older second-level pass.
